# 业务维度分析指南（前端 / 后端）

本文档补充 **业务语义维度** 的分析要点，与 `frontend-analysis-guide.md`、`backend-analysis-guide.md`（技术维度）配合使用。

**职责边界**：
- 技术维度文档 `explain-project.md` 讲「项目怎么建的」：技术栈、结构、约定、资源、部署。
- 业务维度文档 `explain-business-*.md` 讲「项目做什么、为什么」：业务总结、功能模块、接口场景、权限、数据模型、上下游、流程图、核心交互。
- 重叠章节（如「主要功能模块」）在两份文档中**侧重不同**：技术文档侧重目录与代码组织，业务文档侧重业务语义与用户价值。避免两边各写一大段重复内容。

## 端判定与产出规则

沿用 SKILL.md 的仓库类型识别结果：

| 仓库特征 | 产出业务文档 |
|----------|--------------|
| 仅有前端工程（`package.json` 驱动，无后端服务代码） | `explain-business-frontend.md` |
| 仅有后端工程（`pom.xml`/`build.gradle`/`pyproject.toml` 等） | `explain-business-backend.md` |
| 全栈（前端 + 后端共存） | 两份都产出 |

**全栈去重约定**：共享业务上下文（业务总结、业务角色、业务术语表）以 **后端业务文档为「主」** 完整承载；前端业务文档对这些共享章节只写**前端可见视角的补充**，并引用 `explain-business-backend.md`，不重复长篇。

## 通用业务信息来源（不分端）

优先从以下可验证信息归纳，**勿编造**：

- `README.md`、`docs/`、产品需求文档（若随仓库分发）
- 路由 / 页面 / 菜单配置（反推功能模块与权限）
- Controller / 路由处理器、Service / 用例层（反推业务能力与接口）
- 数据库 schema、实体模型、迁移文件（反推数据模型与状态）
- 配置文件中的第三方接入、MQ、定时任务（反推上下游）
- 日志框架配置、切面 / 中间件（反推日志设计）
- 注释、枚举、状态码、错误码

业务相关文件 Glob 模式：

```text
# 前端业务线索
Glob: "src/router/**/*.{ts,js}" 或 "src/routes/**/*.{ts,js,tsx,jsx}"
Glob: "src/pages/**/*.vue" 或 "src/pages/**/*.{tsx,jsx}"
Glob: "src/api/**/*.{ts,js}"
Glob: "src/**/permission*.{ts,js}" 或 "src/**/guard*.{ts,js}"

# 后端业务线索（Java）
Glob: "src/main/java/**/controller/**/*.java"
Glob: "src/main/java/**/service/**/*.java"
Glob: "src/main/java/**/entity/**/*.java" 或 "**/domain/**/*.java"
Glob: "src/main/resources/**/*.sql" 或 "**/db/migration/**"

# 后端业务线索（Python）
Glob: "**/views.py" 或 "**/routers/**/*.py" 或 "**/routes/**/*.py"
Glob: "**/models.py" 或 "**/models/**/*.py"
Glob: "**/migrations/**/*.py"
```

## 前端业务分析

前端业务文档 `explain-business-frontend.md` 侧重**用户可见的业务能力与交互**。

### 1. 业务总结
一句话讲清这个前端为哪类用户解决什么问题、核心价值。

### 2. 业务角色与参与者
- 面向的角色（如普通用户、运营、管理员）
- 各角色在前端能做的事

### 3. 主要功能模块
按**页面 / 功能域**组织，不是按目录。每个模块说明：用途、对应路由、主要操作。
- 例：「订单管理」→ 路由 `/order/*`，操作：列表、详情、取消、退款

### 4. 调用的后端接口及使用场景
- 接口与触发场景的对应关系（不是接口契约本身）
- 例：下单页提交 → `POST /orders`，场景：用户确认购物车后下单

### 5. 权限设计及控制（前端侧）
- 路由守卫 / 菜单权限 / 按钮级权限
- 角色与可见功能的映射
- 注意：前端权限只是体验层，真实权限以后端为准（需在文档中注明）

### 6. 业务流程图（mermaid）
前端参与的关键业务流程，用 `flowchart` 表达页面跳转与用户操作。

### 7. 关键状态机（前端可见）
前端能感知的状态流转（如订单状态：待支付→已支付→已发货），用 `stateDiagram-v2`。后端为权威的，注明来源。

### 8. 业务规则与约束（前端侧）
- 表单校验、限额、必填项、联动逻辑
- 前端兜底与边界提示

### 9. 业务核心交互明细
挑选 2–4 个核心交互，逐步描述：触发→请求→响应→状态变化→UI 反馈。

### 10. 业务术语表（前端相关）
前端代码与产品文案中的领域术语对照。

## 后端业务分析

后端业务文档 `explain-business-backend.md` 是**业务语义的主文档**，覆盖数据、权限、上下游、日志、事件。

### 1. 业务总结
系统承担的业务职责、对外提供的能力、在整体业务中的位置。

### 2. 业务角色与参与者
- 系统涉及的业务角色（含调用方系统）
- 角色与业务能力的映射

### 3. 主要功能模块
按**业务域 / 模块**组织，每个模块：职责、对外能力、关键 Service。

### 4. 对外接口设计及使用场景
- 按业务域分组列接口：方法+路径、用途、调用方、典型场景、是否幂等
- 不必逐字段列参数（契约细节指向技术文档或 OpenAPI），重点是「这个接口为什么存在、谁用」

### 5. 权限设计及控制
- 鉴权方式（Session/JWT/OAuth/API Key 等）
- 角色与权限模型（RBAC/ABAC/数据权限）
- 权限校验落点（拦截器/注解/中间件/网关）
- 越权防护要点

### 6. 数据库设计
- 核心实体与关系（用 mermaid `erDiagram`）
- 关键表用途、主从关系、分库分表（若有）
- 迁移与版本管理（Flyway/Liquibase/Alembic/Django migrations）

### 7. 上下游关联服务
- 上游（谁调用本服务）：协议、入口、QPS 量级（若可得知）
- 下游（本服务依赖）：DB、缓存、MQ、第三方 API、定时任务
- 用 mermaid `flowchart` 画服务拓扑

### 8. 日志设计及控制
- 日志框架与配置（级别、格式、输出位置）
- 关键业务日志：在哪打、记什么（审计日志、操作日志、异常日志）
- 链路追踪（traceId / MDC / OpenTelemetry）

### 9. 领域事件与通知
- 事件发布 / 订阅（MQ topic、事件名、触发条件、消费方）
- 通知机制（站内信、 webhook、推送）

### 10. 业务流程图与状态机（mermaid）
- 跨域流程用 `flowchart`
- 核心实体状态机用 `stateDiagram-v2`（如订单、工单、审批）

### 11. 业务规则与约束
- 业务校验规则、限额、SLA、一致性约束
- 异常与补偿（重试、回滚、对账）

### 12. 业务核心交互明细
挑选 2–4 个核心链路，逐步描述：入口→校验→业务执行→副作用（DB 写、事件、下游调用）→响应。

### 13. 业务术语表
领域术语对照表（术语 / 含义 / 别名），作为前端业务文档的引用源。

## 输出与注意事项

1. **先读可验证信息**：README、路由、Controller/Service、schema、配置，再归纳业务语义。
2. **勿编造业务意图**：无法从代码/文档确认的，标「待补充」或「推测：…」，不要当事实写。
3. **分端取舍**：标注「仅前端」「仅后端」的章节按产出端删除；全栈时前端文档引用后端文档的共享章节。
4. **图优于文字**：流程、状态、ER、拓扑尽量用 mermaid 图。
5. **边界清晰**：业务文档不重复技术文档的构建/部署/约定细节，必要时用链接指向。
6. 最终章节填充以 `assets/explain-business-template.md` 为骨架。
