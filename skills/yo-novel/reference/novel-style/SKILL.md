# novel-style

从一本已有小说中"逆向工程"出一份结构化、可复用的写作风格指南。目标是让后续的 `novel-write` 能像使用内置风格（`style-guide.md` / `style-ancient.md` / `style-web-novel.md`）一样，直接引用这份风格档案来仿写同款气质的文字。

## 核心理念

这份技能不是写一篇"读后感"，而是产出一份**工程化的风格规格书**。它要回答的问题是："如果另一支笔想写出和这本书一样的味道，它需要遵守哪些约束？" 因此每一条结论都要尽量落到**可执行、可检验**的层面（句式、节奏、视角、用词 register、信息释放时机），而不是停留在"文笔优美、感人至深"这类无法落地的形容词。

证据来源是这份文档可信度的根基。请严格区分三类证据，并在文档中标注：

- **【例文实证】**：来自用户提供的示例文章内容。这是最高优先级、可逐字引用的证据。只有这一类允许直接引用原文句子。
- **【网评/评论】**：来自联网检索到的书评、文学评论、读者长评。只能转述要点并附来源链接，不得伪造原文引文。
- **【推断】**：基于上述两者合理外推、但缺乏直接证据的判断。必须显式标注为推断，不让读者误以为是原著特征。

当某一维度三类证据都薄弱时，宁可不写或明确标注"证据不足"，也不要编造。风格指南被仿写时，一条假的"原著特征"比缺失更危险——它会污染所有后续产出。

## 输入

调用本 skill 需要两样东西：

1. **小说名**（必需）。书名要尽量准确，含作者更佳（同名小说很多）。如果用户只给了一个模糊说法（如"那本写三体的"），先和用户确认具体书名与作者。
2. **示例文章内容**（强烈建议，但允许缺省）。一到数段该小说的原文片段，用于做例文实证。可以是直接贴在对话里的文本，也可以是文件路径。如果没有例文，风格提取将主要依赖网评与模型对该作的文学常识，结论的【例文实证】一栏会大量缺失，可信度下降——这种情况要提前告知用户，并降低结论置信度。

可选输入：用户指定只提取其中几个维度、指定输出文件名、指定输出目录。

## 输出位置

- 默认输出到项目根目录下的 `presets/styles/【书名】-style-skill.md`。文件名中的 `【书名】` 用书名本身替换（保留全角方括号 `【】`，例如 `【三体】-style-skill.md`）。如果用户偏好不带括号或改用《》，按用户要求执行。
- 如果 `presets/styles/` 不存在，创建它。这条路径与 `novel-design` 的 `presets/` 约定保持一致，便于集中管理。
- 如果目标文件已存在，**必须先询问用户是覆盖、合并还是跳过**，禁止直接覆盖——风格文档往往是反复迭代的产物。
- 产出后，告诉用户：若希望在 `novel-write` 中直接引用，可把该文件复制/软链到 `novel-write/references/`，或直接在写作时指定 `presets/styles/【书名】-style-skill.md` 作为风格参考；`novel-write` 优先使用用户指定的风格。

## 工作流程

### 1. 理解需求与确认门槛

先与用户对齐，**不要拿到书名就闷头检索**。需要确认：

- 书名与作者是否准确（尤其同名作品）。
- 是否提供了例文；若有，是文本还是文件路径。读取文件内容。
- 用户是否只关心部分维度（默认全量，见 `references/dimensions.md`）。
- 输出文件名与目录是否用默认值。
- 是否需要中英双语或仅中文。

**确认门槛（硬性，但允许快速路径）**：

- **常规路径**：向用户展示一份简短的"提取计划"——将检索哪些方向的资料、会覆盖哪些维度、输出到哪个文件、预计例文实证能支撑哪几条。等待用户明确回复（"确认/开始/ok"）后再继续。
- **快速路径**：如果用户已明确给出书名+例文+维度范围+输出路径，可直接进入 Step 2，但仍需先告知一句"将输出到 <路径>"并等待用户确认落盘路径。

计划示例：

```markdown
将为《三体》提取风格档案：
- 检索方向：豆瓣长评、知乎文学评论、主流媒体书评
- 覆盖维度：叙事视角、全书风格气质、推进节奏、语言文字质感、冲突与伏笔、世界环境温度、信息释放、对话风格、主角与主要配角性格
- 例文实证：你贴的三段原文
- 输出：presets/styles/【三体】-style-skill.md

确认后开始。
```

### 2. 联网检索评价

使用 `WebSearch` / `WebFetch` 检索该书的外部评价。目的是补全例文无法覆盖的宏观特征（气质、节奏结构、伏笔评价、读者共识），以及交叉验证你对例文的判断。

建议检索方向（按优先级，多路并行）：

- `<书名> 书评 / 长评` —— 读者共识与情感反应。
- `<书名> 写作风格 / 叙事 / 文学分析` —— 偏技术的评论。
- `<书名> 作者 文风 / 叙事特点` —— 作者层面的风格定位。
- `<书名> 伏笔 / 结构 / 节奏` —— 结构层面。
- `<书名> 人物 分析 / 角色塑造` —— 人物维度。
- 英文资料（若该书有外译/外评）：`<title> review literary analysis`、`<title> narrative style`。

检索要点：

- **多源交叉**：任一单篇评论都可能带偏见或事实错误。关键结论至少要有两个独立来源相互印证，否则降级为【推断】。
- **中文作品注意**：WebSearch 偏英文环境，对中文小说覆盖有限。对豆瓣、知乎、专业书评站的内容，优先用 `WebFetch` 直接抓取具体页面。抓取失败不要硬编，转而更多依赖例文。
- **可溯源**：每条【网评/评论】结论都要附来源 URL，便于用户复核。抓取到的页面要点用你自己的话转述，不要伪造成原文引文。
- **不可检索时的降级**：如果某本书几乎搜不到有价值的外部评价（冷门/小众/新近作品），明确告知用户，将重心转向例文实证+文学常识推断，并在输出文档顶部注明"本档案主要基于例文实证与推断，网评证据薄弱"。

### 3. 例文细读

把用户提供的例文当作"指纹"。对它做一次细粒度拆解，作为所有【例文实证】的来源：

- 句式：长短句比例、是否善用短句制造冲击、复句嵌套程度。
- 用词 register：书面/口语/方言/术语/古语词的比例，生僻度。
- 修辞偏好：比喻密度与喻体来源域（科技/自然/日常）、排比、反讽、留白。
- 视角与叙述距离：人称、限知/全知、叙述者与人物的心理贴近度。
- 对话：人物语言辨识度、潜台词、对话与动作描写比例。
- 节奏：单位字数内场景切换次数、时间跳跃处理。
- 感官与意象：视觉/听觉/触觉比重，反复出现的意象。

只有例文里**真实出现的句子**，才能在输出中作为引文出现（用引号标出并注明"见例文第 X 段"）。其余一律不得伪造引文。

### 4. 多维度提取

按 `references/dimensions.md` 的维度清单逐条提取。每个维度的产出都要包含：

- **特征描述**：一句话概括该维度上的原著表现。
- **证据**：标注【例文实证】/【网评/评论】/【推断】，例文实证附引文与出处，网评附来源链接。
- **可仿写要点**：落到可执行的层面（"短句占比 ≥40%，用比喻时喻体取自科技域"），而不是"语言精炼有力"。
- **置信度**：高/中/低，三类证据的完备程度。

### 5. 防跑偏清单

仿写最大的风险不是"写不像"，而是"写过头"——把原著某个特征无限放大、或把不适合该场景的特征硬套上去。本步骤要产出一份针对**这本书**的防跑偏清单。

方法：基于 `references/anti-drift.md` 的通用跑偏框架，结合第 4 步提取出的维度特征，逐条推导"仿写这本书时最容易犯的错"。每条采用统一格式：

```markdown
- 【跑偏点】<一句话点名风险>
  - 典型表现：<具体怎么就跑偏了>
  - 防范做法：<可执行的约束或自检问题>
```

例如，仿写一本硬科幻时常见跑偏："把设定当科普，人物沦为设定工具人"——典型表现是连续两页都在讲技术原理、角色没有动机；防范做法是"任何设定披露必须挂在一个有情绪诉求的角色动作上，超过 3 句纯设定就停下来问'谁在着急、为什么'"。

清单控制在 6–10 条，聚焦这本书**特有**的高频风险，不要泛泛而谈"注意不要流水账"这种放之四海皆准的话。

### 6. 生成风格文档

按 `references/output-template.md` 的结构组装最终文档，写入 `presets/styles/【书名】-style-skill.md`。组装时：

- 顶部写明书名、作者、生成日期、证据构成比例（例文/网评/推断各占多少）、整体置信度。
- 各维度按统一小节呈现（特征/证据/可仿写要点/置信度）。
- 防跑偏清单单列一节。
- 末尾留"适用场景"与"与内置风格的差异"两小节，帮助 `novel-write` 判断何时该用这份档案、它和 `style-guide.md` 里哪些内置风格接近或冲突。
- 末尾附"参考来源"列表，列出所有用到的网评 URL。

### 7. 自检与交付

落盘前过一遍自检：

- [ ] 每条维度结论都标了证据类型，没有把【推断】伪装成【例文实证】或【网评】。
- [ ] 所有引文都真实来自用户提供的例文，没有伪造。
- [ ] 所有网评结论都附了来源链接，且为转述而非伪造引文。
- [ ] "可仿写要点"每条都落到可执行层面，没有空泛形容词。
- [ ] 防跑偏清单 6–10 条，针对这本书而非通用废话。
- [ ] 输出文件路径与用户确认的一致；若曾存在同名文件，已按用户选择处理。
- [ ] 文档顶部如实标注了证据薄弱维度与整体置信度。

自检通过后写入文件，并向用户回报：输出路径、证据构成、置信度、哪些维度证据不足需要用户补例文或补资料。

## 何时不要用本 skill

- 用户想从零设计一本**全新**小说的风格——那是 `novel-design` 的职责。
- 用户想直接**写正文**——把已提取的风格档案交给 `novel-write`。
- 用户只想随便聊聊一本书好不好看、不打算落盘成可复用文档——直接聊即可，不必调用本 skill。
- 用户提供的"小说"其实是没有定型的零散点子，无原作可提取——本 skill 依赖一本**已存在**的原著作为分析对象。
